# 09 · 共享服务蔓延

> 什么时候不该拆微服务。这是微服务最容易踩的反模式。

## 反模式：共享服务蔓延（Shared Service Sprawl）

**定义**：把太多"基础能力"抽成共享微服务，导致所有业务都依赖它们。

```
┌────────────┐    ┌────────────┐    ┌────────────┐
│  商城      │    │  CMS       │    │  博客      │
└──────┬─────┘    └──────┬─────┘    └──────┬─────┘
       │                 │                  │
       └────────┬────────┴──────────┬───────┘
                │                   │
        ┌───────┴───┐       ┌──────┴──────┐
        │ 用户服务  │       │ 通知服务    │
        └───────────┘       └─────────────┘
```

**问题**：
- 用户服务挂了 = 所有业务瘫痪
- 加个字段要协调所有消费者
- 部署顺序复杂（必须先升级用户服务）
- "微服务"反而比单体更难维护

## 为什么容易踩坑

### 直觉误区 1："统一账户 = 抽用户服务"

**直觉**：所有项目都要登录，那就抽一个用户服务大家共用。

**现实**：
- 每个项目的"用户"含义不同（商城客户 vs 系统管理员 vs 内容作者）
- 商城要注册、CMS 要权限、博客要评论——业务模型差异大
- 抽出来反而要写更多适配代码

**正确做法**：
- 各自保留轻量用户表（或独立数据库）
- 跨项目登录用 **SSO（OAuth/OIDC）**，不是共享数据库
- SSO 只共享"登录态"，不共享"用户数据"

### 直觉误区 2："代码复用 = 抽服务"

**直觉**：很多项目都要发邮件，抽个邮件服务。

**现实**：
- 邮件发送频率低，没必要独立部署
- 抽成服务后多了网络开销、故障隔离、契约管理
- 直接用 mailgun/sendgrid 的 SDK 就够了

**正确做法**：
- 简单工具（邮件、SMS、文件上传）直接调第三方 SDK
- 不要为了"复用"硬抽服务

### 直觉误区 3："微服务 = 拆分越细越好"

**直觉**：用户、权限、角色、审计、通知都拆成独立服务。

**现实**：
- 5 个服务协调 1 个登录，复杂度爆炸
- 跨服务事务、最终一致性、分布式追踪……全要学
- 团队小、业务简单的情况下完全没必要

**正确做法**：
- 先按业务能力拆（不是按代码模块）
- 一个团队能维护、一个数据库能搞定 → 不要拆

## 什么时候该拆微服务

### 适合拆

| 信号 | 说明 |
|------|------|
| 团队独立 | 不同团队维护，独立部署 |
| 业务边界清晰 | 限界上下文（DDD）天然分离 |
| 独立扩展需求 | 某些服务需要横向扩展，其他不需要 |
| 技术栈差异 | 计算密集型用 Go，IO 密集型用 Node |
| 故障隔离 | 关键服务需要独立 SLA |
| 数据模型不同 | 实时数据 vs 历史数据，存储需求差异大 |

### 不适合拆

| 信号 | 说明 |
|------|------|
| 单体还能跑 | 没遇到性能/团队瓶颈 |
| 业务紧耦合 | 改了 A 必然要改 B |
| 团队小 | 没人力维护多服务 |
| 共享数据多 | 一个事务跨 3 个表 |
| 部署频繁 | 每次改都要发 3 个服务 |

## 渐进式迁移（绞杀者模式）

**Strangler Fig Pattern**：不是一次性重写，是从单体逐步剥离。

```
阶段 1: 单体
┌──────────────────┐
│  单体应用         │
│  - 用户         │
│  - 商品         │
│  - 订单         │
└──────────────────┘

阶段 2: 加 API 网关，部分剥离
┌──────┐    ┌──────────────┐
│ 网关 │◄───│  单体（大部分）│
└──┬───┘    └──────────────┘
   │
   ▼
┌──────┐
│ 用户 │
└──────┘

阶段 3: 继续剥离
┌──────┐
│ 网关 │◄───┐
└──┬───┘   │
   │       │
   ├──> 用户
   ├──> 商品
   └──> 订单（还在单体里）

阶段 4: 单体清空
┌──────┐
│ 网关 │◄───┐
└──┬───┘   │
   │       │
   ├──> 用户
   ├──> 商品
   └──> 订单
```

**优点**：风险可控，随时能回退
**缺点**：长期要维护两套系统

## 微服务 vs 其他架构

### 微服务

**适合**：大型组织、复杂业务、独立团队
**不适合**：小团队、简单业务

### 模块化单体（Modular Monolith）

```
┌──────────────────────────────────────┐
│  单体应用                              │
│  ┌──────┐  ┌──────┐  ┌──────┐      │
│  │ 用户 │  │ 商品 │  │ 订单 │      │
│  └──────┘  └──────┘  └──────┘      │
└──────────────────────────────────────┘
```

**适合**：大多数团队、中等复杂度
**优点**：保留模块边界，但部署简单
**适合**：本项目可以这么拆，但其实直接 3 个独立服务也行

### Serverless

**适合**：事件驱动、流量波动大
**例子**：图片处理、Webhook 处理

### 怎么选

```
团队规模？
├── 1-5 人 → 模块化单体
└── 5+ 人 → 继续问

业务复杂度？
├── 简单 → 模块化单体
└── 复杂 → 继续问

独立部署需求？
├── 没有 → 模块化单体
└── 有 → 微服务
```

## 本项目的设计反思

本项目把"用户管理"单独做成 auth 服务，**有共享服务蔓延的风险**。

反思：

| 维度 | 评价 |
|------|------|
| 团队独立 | ❌ 一个开发者维护 |
| 业务边界 | ⚠️ 用户和业务耦合 |
| 独立扩展 | ❌ 没必要 |
| 故障隔离 | ✅ 演示需要 |
| 数据模型 | ⚠️ 用户表很简单 |

**结论**：生产系统里，本项目这种规模应该用**模块化单体**——一个进程里分 3 个模块，但部署是 1 个。

**但教学场景下**，独立服务能更好地演示故障隔离、服务间调用、trace-id 透传等微服务核心概念。这是刻意的教学选择。

## 真实案例参考

### Netflix（微服务极端）

- 数百个微服务
- 几百个工程师
- 复杂的依赖管理

### Basecamp（模块化单体）

- 30+ 年历史，仍是单体
- 几十人团队
- 强调"简单"

### Slack（先单体后拆分）

- 早期单体
- 业务复杂到必须拆
- 渐进式迁移

## 共享服务的替代方案

如果确实要"共享"，按耦合度从低到高：

### 1. 共享 npm 包（最低耦合）

```
┌──────────────────┐
│  npm 包           │
│  - 用户模型     │
│  - JWT 工具     │
└──────────────────┘
        ▲
   ┌────┴────┐
   │ 项目 A  │
   └─────────┘
```

### 2. Monorepo（中耦合）

```
┌──────────────────────────────────┐
│  monorepo                         │
│  ├── packages/user-model         │
│  ├── packages/jwt-utils         │
│  ├── apps/web                   │
│  └── apps/mobile                │
└──────────────────────────────────┘
```

### 3. 共享数据库（高耦合）

```
┌──────┐      ┌──────┐
│ 项目 A │      │ 项目 B │
└──┬───┘      └──┬───┘
   │             │
   └──────┬──────┘
          │
      ┌───┴───┐
      │ 共享 DB │
      └───────┘
```

**风险**：数据库表结构变更影响所有项目。

### 4. 共享服务（最高耦合）

```
┌──────┐      ┌──────┐
│ 项目 A │      │ 项目 B │
└──┬───┘      └──┬───┘
   │             │
   └──────┬──────┘
          │
      ┌───┴───┐
      │ 用户  │
      │ 服务  │
      └───────┘
```

**风险**：服务挂了全线崩，部署协调复杂。

**经验法则**：能用 npm 包解决，不要抽服务。

## 总结

微服务不是银弹。它适合：

- 大团队、复杂业务、独立扩展需求
- 有专人维护分布式系统的基础设施

不适合：

- 小团队、简单业务
- 想"复用代码"而硬抽服务
- 把所有"基础能力"都抽成共享服务

**决策框架**：

```
1. 业务边界清晰吗？
2. 团队能独立部署吗？
3. 基础设施有人维护吗？
4. 复杂度收益明显吗？

任何一个是 No → 考虑模块化单体
```
